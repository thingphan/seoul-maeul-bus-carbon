## 1. 개요

서울 마을버스는 지하철과 일반버스가 닿지 않는 언덕·골목 주거지를 잇는 생활 교통이다. 수요가 적은 노선은 재정 지표만 보면 감편 대상이 되기 쉽지만, 그 노선에 기대는 고령자에게는 이동 자체를 결정하는 수단이다. 반대로 적은 승객을 위해 큰 차량을 반복 운행하면 탄소 효율이 떨어진다.

본 프로젝트는 공공데이터 24종(원자료 약 110GB)과 교통카드 운행기록 35일분(846,653개 운행)을 결합하여 **어떤 서비스를 지켜야 하는가**와 **어떤 운행의 차량을 바꿀 수 있는가**를 함께 답한다. 같은 도로·속도·경사 조건에서 버스와 승용차의 승객당 탄소를 비교하고, 노선을 없앨 때 고령자가 잃는 접근성을 계산한 뒤, 운행별 최대 탑승을 AI로 예측하고 차량 배치를 최적화하여 소형차 전환이 실제 수요와 운영 제약에서도 성립하는지 검증하였다.

## 2. 문제 제기

- **생활 교통과 재정 압력의 충돌.** 서울시는 2025년 12월 마을버스 재정지원을 412억 원에서 500억 원으로 늘리고 운행을 약 5% 확대하기로 합의했다. 서비스 확충을 탄소중립과 연결하려면 어느 노선을 유지·확대하고 어디에서 차량 규모를 조정할지 판단할 근거가 필요하다.
- **'버스는 친환경'이라는 전제의 조건.** 차량 1대 기준으로 마을버스는 승용차보다 CO₂를 더 배출한다(1km당 461g 대 370g, 노선 중앙값). 버스의 이점은 여러 승객이 배출을 나눌 때만 성립한다.
- **평균 수요의 함정.** 평균 재차인원이 낮은 노선·시간대라도 특정 운행에는 승객이 몰린다. 평균만으로 작은 차를 보내면 정원을 넘는 운행이 생겨 오히려 이동권을 해친다.
- **골목길의 관측 공백.** 서울 도로 링크의 29%는 속도 관측이 없고, 그 공백은 마을버스가 다니는 1차로 골목에 몰려 있다.

## 3. 분석 질문

1. **탄소 효율:** 동일 운행 조건에서 마을버스는 승용차보다 탄소 효율이 높은가? 전기화와 저재차 시간대 소형화에는 어느 정도의 감축 여지가 있는가?
2. **정책 유형:** 탄소 효율과 고령자 의존도를 함께 보면 어떤 노선에서 지원·서비스 유지·차량 규모 조정을 우선 검토해야 하는가?
3. **접근성 손실:** 고령자 의존도가 높은 노선을 제거하면 정류장 접근성이 얼마나 악화되는가?
4. **수송 용량:** 평균 수요가 낮다는 이유만으로 소형화해도 되는가? AI 피크 예측은 전환 후보의 정원 초과 위험을 줄이는가?
5. **운영 조건:** 용량·배터리·차량 수·자료 일관성 조건을 적용하면 어떤 운행이 전환 후보로 남으며, 차량 확보 규모에 따라 감축 효과는 어떻게 달라지는가?

## 5. 분석 방법

![분석 흐름](docs/report/images/integrated/00_full_flow.png)

**1) 경로·속도·수요 결합과 동일 조건의 탄소 비교.** 실제 노선 경로를 방향성 도로망에 매칭하고, 5분 관측속도와 AI 추정 속도, DEM 방향성 경사로 노선별 에너지를 계산하였다. 정류장 순서대로 '승차 − 하차'를 누적하여 평균 재차인원 L(하루 승객·km ÷ 하루 차량·km)을 구했다. 전기차는 VT-CPEM, 승용차는 VT-CPFM 계열과 하이브리드 모형, 경유·CNG 버스는 서울 실측 배출 비율로 계산하고 서울 연료 구성으로 가중하였다. 버스 승객·km당 배출 b/L, 승용차 c/o(o = 1.2명), 손익분기 재차인원 b×o/c로 비교한다. 기준 전기버스(7t)는 카운티 일렉트릭의 정속 주행거리로 공기저항을 보정하고 정지·출발·체류 에너지를 따로 더하였다.

**2) 의존도·노선 제거 접근성과 정책 시나리오.** 고령 비율·고령 생활인구·대체수단 없는 승차 비중의 백분위 순위 평균으로 의존도를 만들고, 의존도와 승객·km당 탄소의 중앙값으로 네 유형을 나눴다. 노선을 하나씩 제거한 뒤 Tobler 보행속도에 고령자 계수 0.75와 경사를 반영한 도로망 Dijkstra로 250m 격자별 접근시간을 다시 계산하였다.

**3) AI 예측과 차량 배치 최적화.** 관측이 없는 도로의 속도를 XGBoost로 추정하고, 교통카드로 재구성한 운행별 최대 탑승을 XGBoost 분위수 회귀로 예측하였다. 보정한 Q99 예측 상한이 정원 이하이고 배터리·차량 수·자료 일관성 조건을 만족하는 차량별 하루 운행 묶음을 MILP로 골라 감축량을 최대화하였다.

## 6. AI 활용

| 기술 | 역할 | 검증 |
| --- | --- | --- |
| 도로 속도 XGBoost | 관측이 없는 도로의 시간대별 속도 추정(A 관측 이력 조회, B 이웃 이력 포함, C 이웃 이력 제외). 마을버스 노선 길이의 13.2%를 보완 | 도로 단위 3-fold GroupKFold(이웃 조회표도 fold별 재구성): B R² 0.72·MAE 4.6km/h, C R² 0.31·MAE 5.7km/h. SHAP 최대 기여는 이웃 도로 속도 |
| 운행 피크 XGBoost | 운행별 최대 탑승의 Q50·Q95·Q99 예측, 직전 7일 수요로 정규화, 보정 주 잔차로 Q99 보정 | 날짜 분리(학습 7/6~19, 보정 7/20~26, 개발 7/27~8/2, 최종 검증 8/3~9), 검증 주는 하루씩 순차 예측. 예측 상한 포함률 99.29% |
| MILP 차량 배치 | 확보 대수·배터리 안에서 교체할 운행 묶음 선택 | 보정 기간에 배분을 정하고 검증 주에 고정해 평가. 한계편익 탐욕법과 최적값 일치 확인 |

생성형 AI(Claude Code, OpenAI Codex)는 데이터 수집·코드 작성, 단위·누수 점검, 정책 해석 검토에 활용하였다. 작업은 '연구자의 질문 설정 → AI의 코드 작성·실행 → 다른 AI의 교차 검토 → 연구자의 채택 판단' 순서로 진행하였다. 이 과정에서 카운티 일렉트릭 주행거리를 복합 값으로 잘못 읽은 에너지 보정 오류를 찾아 전 수치를 다시 계산하였다.

## 7. 정책 제안

노선 유지·지원 판단에는 접근성 손실을, 차량 전환 판단에는 운행별 피크와 에너지 조건을 함께 적용한다. **노선은 지키고, 차량은 운행에 맞게 결정한다.**

| 제안 | 현행 | 실행 |
| --- | --- | --- |
| 1. 지원 심사와 서비스 평가에 탄소·접근성·수송 용량 반영 | 2025.12 합의로 서비스 평가 인센티브 도입 예정(2027년 정착), 평가 지표 미공개 | 심사표에 승객·km당 탄소, 노선 제거 시 고령자 접근성 영향, 피크 수송 용량을 함께 제시. 접근성 손실이 큰 노선 조정은 '피크 고정노선 + 한산 시간 호출형(DRT)'을 전제로, 2026년 증편은 손익분기 전환인원이 낮은 29개 후보부터 |
| 2. 저상버스 예외 노선의 소형 저상 전기차 단계 전환 | 마을버스도 교체 시 저상버스 의무, 도로 여건상 예외 승인. 2026.10 서울시 조례로 예외 노선의 사유 해소 방안 의무화 | 은평구 예외 노선 중 분석 대상 4개 가운데 3개가 '② 소형 차량 전환' 유형. 해소 방안에 소형 저상 전기차를 넣되 피크 예측 상한이 정원 이하인 운행부터 전환 |
| 3. 운행별 적합성을 확인하는 단계적 전환과 보조금 연계 | 친환경 마을버스 보조금은 차종별 대당 정액, 노선 수요 적합성 기준 없음 | 중랑01·서초05·서초01의 일부 운행 묶음에서 시범운행(비교군 운영), 보조금 배정에 '운행별 수요 검증 통과' 요건 |

세부 근거와 성과지표는 [보고서 본문의 정책제안](docs/report/maeul_bus_integrated_report.md#정책제안-및-기대효과)에 있다.

## 8. 한계

- 노선별 실제 차량 정보가 없어 공통 중형 차량과 서울 연료 구성을 적용하였다(대형 비중은 버스 배출 1.28·1.5배 민감도로 검토, 18조건에서 버스 우위 157~223개).
- 에너지 모형은 공인값으로 보정한 근사이며, 정지·출발·체류 에너지는 가정이다. 실차 충전·연료 기록으로 검증하지 않았다.
- 교통카드 기반 피크는 태그하지 않은 승객을 관측하지 못한다. 차량 배치 운행의 15.7%는 태그 품질상 정원 검증이 불가능했다.
- 소형차 제원(휠체어 배치 16명·105kWh)은 국내 인증 차종이 아니며, 차고지·충전·근무표는 현장 확인이 필요하다.
- 접근성 손실은 가장 가까운 정류장까지의 보행만 반영하여 목적지·배차 차이에 따른 부담은 포함하지 않는다.
- 시간대 잠재량(7월 집계, 230개 노선)과 운행 배치 감축(검증 주, 운행 묶음)은 기간·단위·제약이 달라 합산하지 않는다.

## 10. 재현 방법

Python 3.13에서 검증하였다. 원자료는 저장소에 포함하지 않으므로 [데이터 명세](data/README.md)의 출처에서 내려받아 같은 경로에 둔다. API 인증키는 코드와 저장소에 넣지 않고 환경변수로만 읽는다.

```powershell
pip install -r requirements.txt
python -X utf8 -m unittest discover -s tests -v      # 테스트 19개
$env:SEOUL_BUS_API_KEY = "<서울시 버스운행정보 API 키>"
$env:KMA_API_KEY = "<기상청 API허브 키>"
```

**1단계: 도로 속도 데이터와 AI 속도 모델.** 학습된 모델과 조회표가 저장소에 있어 재학습 없이 예측할 수 있다.

```powershell
python src/models/04_batch_predict_all_link_speed.py --start-date 20260707 --end-date 20260720
```

원자료부터 다시 만들 때는 다음 순서로 실행한다.

```powershell
python src/pipeline/01_extract_seoul_links.py
python src/pipeline/02_aggregate_5min_speed.py
python src/pipeline/03_fetch_kma_radar.py --from-5min-times
python src/pipeline/04_build_link_dimension.py
python src/pipeline/05_build_speed_fact.py
python src/models/01_build_model_a.py
python src/models/02_build_model_bc.py --mode validate          # 도로 단위 GroupKFold 검증
python src/models/02_build_model_bc.py --mode final
python src/models/04_batch_predict_all_link_speed.py --start-date 20260707 --end-date 20260720
```

**2단계: 마을버스 기본 분석(01~10).** 노선 맵매칭, 재차인원, 의존도, 접근성 등 통합 재계산의 입력을 만든다.

```powershell
python src/transit/01_build_bus_route_links.py
python src/transit/02_build_route_demand.py
python src/transit/03_build_route_feasibility.py
python src/transit/04_build_route_energy.py
python src/transit/05_build_route_carbon_breakeven.py
python src/transit/06_classify_route_priority.py
python src/transit/07_build_route_operations.py
python src/transit/08_access_gap.py
python src/transit/09_validate_ai_speed.py
python src/transit/10_route_removal_access.py
```

**3단계: 운행 피크 AI·차량 배치와 보고서 수치.** 교통카드 원자료를 공개 원본에서 받아 운행 재구성부터 배치·민감도까지 실행하고, 수정한 에너지로 탄소·접근성을 `data/processed/transit_full/`에 다시 계산한다.

```powershell
pip install xgboost==3.4.0                                   # 운행 피크 모델 결과를 그대로 재현하는 버전
python -X utf8 -m src.transit.upgrade.run --download --integrated
```

이미 받은 카드 자료를 쓸 때는 `--download`를 뺀다. 통합 단계만 다시 실행하려면 `python -X utf8 -m src.transit.upgrade.integrated`를 쓴다. 보고서 초안 PDF(`src.transit.upgrade.integrated_report`)에는 `requirements-upgrade.txt`의 reportlab·PyMuPDF가 추가로 필요하다. 세부 입력 계약과 기간은 [운행 검증 안내](docs/MAEUL_UPGRADE_IMPLEMENTATION.md)와 [통합 재현 안내](docs/MAEUL_INTEGRATED_REPORT.md)에 있다.

**검증 기록.** 새로 복제한 저장소에서 위 순서를 실행해 마을버스 기본 산출물과 저장된 속도 모델의 전 링크 예측이 기존 결과와 일치함을 확인하였다. 운행 피크 모델과 차량 배치 결과(`model_metrics.csv`, `policy_metrics.csv`)는 기본 환경에 xgboost 3.4.0을 설치한 상태에서 제출 보고서 수치와 같게 재현되었다. xgboost 버전이 다르면 피크 예측값이 미세하게 달라질 수 있다.
